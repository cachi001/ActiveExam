## Why

Hoy el alumno "rinde" un examen que es una maqueta: una sola pregunta hardcodeada en `frontend/src/screens/Examen.tsx`, sin modelo de preguntas en la DB y sin forma de cargar el banco real de la cátedra. Además el flujo de examen muestra al alumno un toast por CADA evento de proctoring detectado (filtra la lógica de detección al examinado) y no fuerza pantalla completa, por lo que el alumno puede salir del examen sin fricción. El dueño decidió (2026-06-26) construir una experiencia de rendición REAL **dentro de la plataforma**: preguntas en la DB alimentadas por un importador de **Moodle XML**, sin toasts de eventos, con lockdown de pantalla completa.

El dueño aclaró además (2026-06-26) que el objetivo NO es sólo rendir el examen en la plataforma, sino que **la NOTA del examen impacte de vuelta en Moodle**. La integración con Moodle es por lo tanto **bidireccional**: el contenido entra por **lectura** (import de Moodle XML) y la nota vuelve por **escritura** hacia Moodle. El camino de escritura elegido y confirmado por el dueño es la **REST Web Service de Moodle `core_grades_update_grades`** (NO LTI 1.3/AGS — eso queda como evolución futura). Sin este pilar de write-back el ciclo queda incompleto: el alumno rinde dentro de la plataforma pero su calificación no se refleja donde la cátedra la gestiona.

**BREAKING — cambio de postura del proyecto**: esta decisión **anula (supersedes) DD-20** y la visión declarada ("operar el examen mismo está fuera de alcance"), y **revive el scope que canceló c-44**. Hasta hoy el contrato del proyecto era: *el LMS opera el examen; el proctoring NO lo crea ni lo importa, se integra alrededor*. A partir de este change, la plataforma SÍ opera el examen (preguntas, respuestas, render de rendición). El dueño confirmó la anulación explícitamente.

## What Changes

- **Quitar los toasts de eventos durante el examen** (`Examen.tsx`, useEffect ~líneas 107-122 + el mapa `SEV_TOAST`). El alumno deja de ver el feedback por evento (`Rostro ausente · Alta · +X pts`). Los eventos se siguen detectando, scoreando y persistiendo server-side EXACTAMENTE igual; sólo se elimina la notificación visible al alumno. El panel lateral de "Señales de integridad" y el modal de monitor adicional son decisión aparte (este change quita SOLO el toast por evento; ver design.md sobre el alcance del panel).
- **Modelo de examen propio con preguntas en la DB** (Postgres slim, Alembic aditiva). Nuevas tablas: examen de contenido + preguntas + opciones, con marca de opción correcta. API de lectura para rendir (sin exponer la respuesta correcta al alumno) y API/servicio de ingesta. Hoy las preguntas están hardcodeadas y el CRUD existente (`backend/.../api/v1/exams/`) modela la *configuración de proctoring* del examen, NO su contenido de preguntas.
- **Importador de Moodle XML** (camino de LECTURA). El admin sube el export "Moodle XML" del banco/quiz; se parsea y se ingiere a nuestro modelo de examen. Se eligió **Moodle XML** (no la REST API de Moodle) para traer el CONTENIDO porque las Web Services del core de Moodle **no exponen el contenido de las preguntas**; el XML sí. (Listar cursos/quizzes y traer el banco por API sigue fuera de alcance; LTI 1.3/AGS/NRPS y el plugin `quizaccess` también — ver "Fuera de alcance".)
- **Write-back de la nota a Moodle** (camino de ESCRITURA — pilar central de este change). Al finalizar la sesión de examen, el backend calcula la **nota académica** (respuestas correctas, server-side) y la escribe en Moodle invocando la REST Web Service **`core_grades_update_grades`**. El admin provee la base URL de Moodle, el **token** (guardado como secreto en Vault/secret manager — nunca en el cliente ni en el repo), el `courseid` y el ítem de calificación / `cmid` destino. El alumno se mapea al usuario Moodle por `idnumber` (default) con fallback por email. El envío es **idempotente con reintentos**, persiste su estado y queda **auditado**; si Moodle no responde, la finalización del examen NO se bloquea y el envío queda reintenable. Coherente con L2.5: se escribe la **nota académica**, NUNCA el score/flags de proctoring.
- **Lockdown de pantalla completa al rendir** (Fullscreen API). Al iniciar el examen se entra a fullscreen y el alumno no puede salir ni minimizar hasta finalizar. Ya existe DETECCIÓN (`contextDetectors.ts`: `FullscreenDetector`/`FocusDetector`; `useExamProctoring.ts`) que hoy SÓLO registra evento + suma score. Se agrega **ENFORCEMENT**: forzar fullscreen al iniciar; ante salida de fullscreen / blur / pestaña oculta → overlay de bloqueo que tapa el examen + re-forzar fullscreen hasta que el alumno vuelva. **Límite honesto documentado** (coherente con DD-21: web app, no lockdown nativo L5): el navegador NO puede impedir el minimize del SO ni ver fuera del sandbox; se DETECTA y se REACCIONA (bloquea + re-fuerza), no se previene a nivel SO. La detección+score existente NO se rompe: el enforcement se suma encima.

## Capabilities

### New Capabilities
- `exam-content-model`: modelo de dominio + persistencia (tablas slim) de examen de contenido, preguntas, opciones y marca de opción correcta; reglas de integridad (al menos N opciones, exactamente una correcta para opción múltiple).
- `exam-taking-api`: API de lectura para rendir un examen — devuelve preguntas y opciones al alumno habilitado **sin** filtrar la opción correcta; orden estable de preguntas.
- `moodle-xml-import`: ingesta del formato Moodle XML (multichoice / truefalse al menos) hacia el modelo `exam-content-model`; admin-only; reporta preguntas importadas y omitidas; idempotente / re-importable de forma controlada.
- `moodle-grade-writeback`: al finalizar el examen, cálculo de la nota académica server-side y escritura en Moodle vía REST WS `core_grades_update_grades`; mapeo alumno↔usuario Moodle (idnumber default, email fallback); idempotencia/reintentos, estado persistido, manejo de error si Moodle no responde y auditoría del envío. Escribe sólo nota académica (L2.5: nunca score/flags de proctoring).
- `exam-fullscreen-lockdown`: enforcement de pantalla completa durante la rendición — forzar fullscreen al iniciar, overlay de bloqueo + re-forzado ante salida de fullscreen/blur/pestaña oculta, con el límite SO documentado. Consume el `FullscreenDetector`/`FocusDetector` existentes (sin modificarlos): el detector sigue produciendo la misma señal hacia el score; el enforcement es una capa nueva encima.
- `student-exam-rendering`: experiencia de rendición del alumno — renderiza las preguntas/opciones reales servidas por `exam-taking-api` (reemplaza la pregunta hardcodeada) y NO notifica al alumno cada evento de proctoring por toast (se elimina el feedback por evento; la detección/score server-side no cambia).

### Modified Capabilities
- (ninguna a nivel de requisitos de spec.) Los detectores de `browser-context-detectors` NO cambian su contrato: siguen produciendo las mismas señales. El enforcement de lockdown y la remoción del toast se modelan como capabilities NUEVAS (`exam-fullscreen-lockdown`, `student-exam-rendering`) que consumen lo existente sin alterar su comportamiento. Se evita un delta MODIFIED para no perder detalle del spec vigente.

## Impact

- **Frontend**: `frontend/src/screens/Examen.tsx` (quitar toasts; cablear preguntas reales desde la API; entrar a fullscreen al montar; renderizar overlay de bloqueo), nuevo módulo de enforcement de fullscreen (p. ej. `frontend/src/proctoring/fullscreenLockdown.ts`), consumo de la nueva API de rendición, pantalla/acción admin de import de Moodle XML.
- **Backend**: nuevo dominio `exam_content` (entidades + repos), nueva migración Alembic aditiva (rama slim, sigue 0025), nuevos endpoints bajo `/api/v1` (lectura para rendir + import admin-only), schemas Pydantic con `extra='forbid'`. Para el write-back: cliente Moodle REST server-side (httpx async) que invoca `core_grades_update_grades`, servicio de cálculo de nota académica, servicio de write-back con idempotencia/reintentos, disparo al finalizar la sesión de examen, tabla/estado de envío + entradas de audit log. El token de Moodle se inyecta desde el secret manager (Vault), nunca embebido.
- **DB**: tablas nuevas (examen de contenido / preguntas / opciones). Aditivo, no toca tablas existentes (patrón de 0023).
- **KB / decisiones (al archivar)**: actualizar **DD-20** (`knowledge-base/09_decisiones_y_supuestos.md:109-120`) para reflejar que la plataforma ahora SÍ opera el examen vía importación **y devuelve la nota a Moodle por REST WS `core_grades_update_grades`**, y actualizar la **nota de cancelación de c-44** (`archive/<fecha>-c-44-*-CANCELLED/` + `CHANGES.md` líneas ~21) para indicar que su scope fue revivido por c-69. La integración LTI 1.3/AGS/NRPS y el plugin Moodle `quizaccess` siguen siendo change futuro aparte (el retorno de nota por REST WS de hoy NO es AGS).
- **Reglas duras**: L2.5 intacto (el examen no sanciona; el lockdown bloquea/re-fuerza, no expulsa ni anula la sesión; **la nota que vuelve a Moodle es la académica, NUNCA el score/flags de proctoring**). Cliente = sensor no confiable: la corrección de respuestas, el resguardo de la opción correcta y el **write-back de la nota** son server-side; el cliente nunca recibe la respuesta correcta ni invoca/transporta el token de Moodle. Ley 25.326: el contenido de preguntas no es dato sensible, pero el import admin-only, la no-exposición de la opción correcta y el resguardo del token (secret manager) se respetan.
- **Fuera de alcance (explícito)**: **listar cursos/quizzes o traer contenido por la REST API de Moodle** (el contenido entra por XML), **LTI 1.3, AGS, NRPS (roster), plugin `quizaccess`**, tipos de pregunta complejos de Moodle (cloze/drag-drop/calculated) más allá de los soportados, feedback por pregunta avanzado. **En alcance** (vía REST WS, no LTI/AGS): el **write-back de la nota académica** por `core_grades_update_grades`.
